## arquitetura
- Sem formulário de cadastro de aluno na interface, porque a TASK-011 não o prevê. Nos E2E, o aluno é criado por `POST /api/students` com a sessão real do usuário. A validação de e-mail duplicado e de CPF inválido é conferida na API (409 `EMAIL_IN_USE`, 400 com `details.cpf = "CPF inválido"`). A mensagem na tela é conferida na edição inline do detalhe, que hoje é a única tela que grava aluno. Se o formulário for construído, o teste da mensagem na tela precisa de mais um passo.
- O RBAC de alunos é verificado no backend, não só na tela: cada cenário de papel chama `/api/students` pelo `page.request`, com o cookie da sessão real. São conferidos o 404 no GET/PUT de aluno de outro vendedor e o 403 `FORBIDDEN` no DELETE para CEO e vendedor.
- Aluno de outro vendedor aberto por URL responde 404 `NOT_FOUND` ("Aluno não encontrado"), não 403. O backend não revela que o registro existe.
- Quando o vendedor cria um aluno com `assignedTo` de outra pessoa, o backend grava o próprio vendedor como responsável.
- A exclusão de aluno grava um `AuditLog` `STUDENT_DELETED` na mesma transação, com o id do admin como autor e `metadata.student` contendo id, nome e e-mail do aluno.
- O `TRUNCATE` do `globalSetup` do E2E lista de forma explícita os models de negócio (`Students`, `Courses`, `Purchases`, `PipelineLeads`, `Tasks`), além de `Users` e `AuditLogs`. Aluno sem responsável e curso não dependem de `Users`, então o `CASCADE` a partir de `Users` não os apaga. Sem isso, um spec poderia herdar alunos de uma execução anterior.

## padrao
- Para testar RBAC entre vendedores, há uma segunda vendedora nas fixtures (`otherVendedorUser`), dona dos alunos que o vendedor principal não pode ver.
- Os dados de teste são únicos por teste: `uniqueEmail(prefixo)` e `randomValidCpf()`, que gera CPF aleatório com dígitos verificadores válidos e nunca uma sequência repetida, que o backend recusa. Isso evita colisão no `@unique` entre testes.
- O debounce da busca é testado digitando tecla a tecla com intervalo curto (20 ms). O teste confere que só sai requisição com o termo completo e que o termo vai para a URL.
- Edição inline é validada depois de um reload e também pela API.
- Toda exclusão é testada nos dois caminhos: cancelar não apaga; confirmar dá DELETE 204, mostra o aviso, tira o aluno da lista (inclusive após reload) e a API passa a responder 404.
- Asserções direto no banco nos E2E passam antes por `assertTestDatabase`, que garante que o banco é `crm_alunos_test`.
- Os seletores são por role e label. Mensagens de erro são buscadas dentro do card/section que as contém (ex.: card "Dados pessoais"), nunca com `getByRole('alert')` global, que colide com o anunciador de rota do Next em modo estrito.
- Todo spec novo entra na tabela de `tests/e2e/README.md`.
- Na verificação, a saída de cada comando vai para um log em `$TEMP`. O exit code é lido direto do comando, sem pipe, e os números vêm do log com grep (`Tests:`, `Test Suites:`, `All files`, `passed/failed`, `Compiled`).
- Para garantir que o spec E2E passa pelo typecheck, confere-se com `npx tsc --noEmit --listFilesOnly | grep students.spec`.
- Antes do `e2e` e do `build`, confere-se no Windows que as portas 3000/3001/3100/3101 estão livres, com `Get-NetTCPConnection -State Listen`. Depois do e2e, confere-se de novo que não ficou servidor órfão.
- A ordem da verificação completa é: typecheck → test → test:coverage → test:integration → e2e → build.

## falha
- Não é verdade que a Sprint 6 tem tela de cadastro de aluno. Um E2E de "admin cria aluno pela UI" não tem onde rodar, e a mensagem de e-mail duplicado ou CPF inválido "no cadastro" não pode ser conferida em formulário de criação. É preciso confirmar no código (`src/pages/students`, `src/components/Students`) que a tela existe antes de escrever o cenário.
- Aluno sem responsável e curso não são apagados pelo `TRUNCATE "Users", "AuditLogs" ... CASCADE`, porque não dependem de `Users`. Limpar só essas tabelas deixa alunos de uma execução para a outra.
- Em modo estrito, `getByRole('alert')` casa também o anunciador de rota do Next e quebra a asserção. Não serve como seletor global de mensagem de erro.
- O exit code de um comando com pipe (`npm run ... | tail`) não indica se o comando passou.
- O Playwright pode reaproveitar um servidor órfão nas portas 3100/3101. Se as portas não forem conferidas antes, o e2e pode rodar contra um servidor que não é o esperado.
